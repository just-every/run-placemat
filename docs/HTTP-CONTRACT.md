# Product HTTP contract

All private GETs require a native active owner/admin/member session (or read-only/preparation agent key). All private POSTs require exact Origin and owner/admin or an explicit product host capability, with owner-only keys, erase, backup/restore and move-in. Agents may only read state and prepare proposals; approval always needs a native person session. JSON errors are `{error:message}`; POST success `{result:...}`.

- GET `/api/state`: `{state, guests, actor, version, names}`; `names` maps each person or preparation key that prepared or approved something to a readable name; guest rows are `{id, name, email, phone, notes, history?}`. State types in src/placemat/model.ts.
- POST `/api/commands`: `{command, payload}`. Commands: `venue.update` {name,timezone}; `table.save` {id?,label,seats,x,y}; `service.save` {id?,name,startAt,endAt,turnMinutes,coverLimit}; `proposal.prepare` {kind,plan,reason}. Plans: service.publish {serviceId}; reminders {serviceId}; table.assign {bookingId,tableIds}. `proposal.approve` / `proposal.decline` {proposalId}; `booking.walkin` {serviceId,name,email?,phone?,partySize,startAt,tableIds?}; `booking.status` {bookingId,status}; `waitlist.add` {serviceId,name,email?,phone?,partySize}; `waitlist.seat` {waitlistId,startAt,tableIds?}; `guest.update` {guestId,notes}; `guest.erase` {guestId,confirm:"ERASE"}.
- GET `/api/public/services`: published service objects plus current availability (no guest data).
- POST `/api/public/book`: {serviceId,name,email,phone?,partySize,startAt}; auto-assigns available table or a combination; 409 when full. Response only booking id and confirmation, no other guest data.
- GET `/api/reminders.csv` person owner/admin: approved reminders exported for venue's own sender. No provider calls.
- GET `/api/calendar/:bookingId` private: calendar download.
- POST `/api/agent-keys` {name}: owner-only one-time secret. DELETE `/api/agent-keys/:id`: revoke.
- GET `/api/business-export/<kind>.csv`: owner only, CSV attachment from one consistent current snapshot. Settings lists supported kinds; [field definitions and exclusions](data-portability.md) describe every column. CSV reads never mark a reminder delivered or change records.
- GET `/api/backup`; POST `/api/restore` {archive,confirm:"RESTORE"}: owner, empty product destination, integrity and erasure fences. A refusal's `error` explains the cause and next step in plain language.
- Move-in endpoints are documented by the importer author in docs/MOVE-IN.md. UI sends CSV text; importer returns dry-run plan then explicit apply, journal and undo.

`/app` floor, operations, guests, approvals and move-in screens share one page with navigation anchors; `/book` is the guest page. Scripts must show server errors and wait for success before updating the screen. Datetimes are ISO UTC; UI labels times in the venue timezone and converts local input via Intl (reject ambiguous/nonexistent times). First setup is empty, never demo data.

### REPORT-001 reservation reports

A signed-in owner/admin reads `GET /api/reports/reservations` or downloads the identical row selection at `GET /api/reports/reservations.csv`. Members and preparation keys cannot export reports. Query filters combine: `venue` (current venue name), `dateFrom` / `dateTo` (inclusive local service-start dates), `serviceId` (shift), `area`, `source`, `status`, `partyMin` / `partyMax` (inclusive 1–500, the largest supported party; omitted means every size), and `period` (`all`, `past`, `current`, `future`, based on the service interval). Omit a filter for all values. Invalid dates, enums and reversed bounds return 400. Unknown venue, area or shift yields no rows.

Booked covers include every matching reservation, including cancellations and no-shows; attended covers are seated/completed reservations. Cancelled/no-show/attended rates divide their covers by all booked covers; a zero denominator is reported as null. Each total includes its booking IDs; CSV contains those same reservation rows, with no guest contacts or notes. A combined-table booking contributes its covers once even when it includes multiple areas. Tables without an area belong to Dining room. Services and booking instants are stored in UTC and rendered in the venue IANA timezone; service dates follow the service start even across midnight or daylight-saving changes.

### GUEST-002 profiles and normalized search

`GET /api/guests?search=...` uses the same native session or preparation-key read authority as `/api/state`. It omits erased guests and matches case/accent-normalized name/email or phone digits, ignoring US punctuation and an optional leading 1; phone suffix lookup is supported. This search does not merge identities: booking still reuses exact normalized email only.

An owner/admin person submits `guest.profile` to `/api/commands` with `guestId` and any of `tags` (up to 20 unique strings), `vipLevel` (`none`, `regular`, `vip`), `seatingPreference`, or `notes`. Unspecified fields remain unchanged. Each changed fact keeps the staff actor/time and explicit source; note changes retain dated history. The existing `guest.update` command remains a note-edit door. No public booking input writes private profile facts. The guest profile shows current bookings and imported visits together; flags and seating preferences also appear beside arrivals in the booking list.

Guest-supplied contacts, staff-observed fields and Tablein-shaped imports have separate provenance. An import lacking an original date says date not recorded; legacy records lacking provenance say source not recorded. No allergy, access need, diagnosis or consent is inferred. Current owner/admin staff edit and existing member/preparation-key readers see the same fields they may already read as guest notes, as ct approved on 19 October. Restricted facts and finer roles introduced by GUEST-003, ROLE-003, ROLE-004 and DATA-004 must enforce their field scopes in every profile/search/arrival/backup door before shipping. Owner erasure removes the profile, note history and provenance with the guest's other personal values.

### SERVICE-004 channel rules

`service.save` accepts `bookingRules` with `online`, `walk-in` and `waitlist` objects. Each has `minParty`, `maxParty`, `horizonDays` (inclusive local calendar days), `leadMinutes` (elapsed; zero disables the staff-seating lead check, while public bookings remain future-only), `sameDayCutoff` (inclusive venue HH:MM), `slotMinutes`, `inquiryAbove`, and `blockedStarts` (offset instants). The public services door filters these rules, and public booking checks them again. Slots align to service start. Staff `booking.walkin` and `waitlist.seat` may pass `overrideReason` for party/horizon/lead rules as owner/admin; the resulting booking keeps the exact violations, actor, timestamp and reason with a `booking.rule-override` audit link. An override never bypasses table fit or clashes. Oversized inquiries are directed to contact the venue; this does not submit or confirm an inquiry.

### SERVICE-006 turns and reset

`service.save.turnPolicy` has `cleanupMinutes`, optional offset `lastSeatingAt`, `partyTurns: [{minSize, maxSize, minutes}]`, `tableTurns: {tableId:minutes}` and `areaTurns: {area:minutes}`. Party ranges do not overlap. Table overrides area, then party range, then service duration; a combination uses the longest constituent turn. Confirmations separate guest `endAt` from table `cleanupEndAt`. Full turn and cleanup must fit service hours and last seating is inclusive. A completed booking with a reset still protects that original reset interval.

To change future rules, prepare `service.turns` through `proposal.prepare` with `{serviceId, turnPolicy}`. The exact proposal includes per-reservation current/proposed times and whether the new policy would exclude it; existing bookings are explicitly preserved. A person approves through `proposal.approve`; any intervening service/floor/booking edit requires renewed review. Experience-specific rules are owed by EXP-001/002 before those capabilities ship.

### WAIT-006 accountable queue

`waitlist.add` returns `queued` with intake time, actor history and an owner. Optional `quoteMin`, `quoteMax`, `basis` record a quoted range; a missing phone creates an owned no-contact follow-up with optional `contactReason`. Current owner/admin staff use these additional commands:

- `waitlist.status` `{waitlistId, status, reason}` records offered, accepted, arrived, declined, expired or abandoned transitions; only `waitlist.seat` creates a capacity-checked booking. Offers/replies are staff observations, not provider sends or inventory holds.
- `waitlist.quote` `{waitlistId, quoteMin, quoteMax, basis}` retains quote history.
- `waitlist.priority` `{waitlistId, priority, reason}` records a higher-first numeric priority and current acting owner.
- `waitlist.followup` `{waitlistId, followUpId, outcome}` completes an owned follow-up with actor and time, including after closure.
- `service.close` `{serviceId, reason}` resolves every remaining queue entry, preserves seated history and disables new public bookings, walk-ins and queue intake for that service. Offered/accepted become expired; other active entries become abandoned, with assigned follow-up. Existing reservations remain.

Actual wait is intake-to-seat or terminal disposition in elapsed minutes; UI rounds to a tenth, and missing legacy observations are labelled not recorded. Legacy waiting/cancelled rows display as queued/declined without inventing dates. Erasure removes linked operational free text and copied service-close instructions while retaining anonymous timings and accountability.

### SERVICE-002 recurring schedules

Owner/admin commands use `/api/commands`. `schedule.save` accepts `{id?, name, shift, seasonStart, seasonEnd, weekdays, startTime, endTime, turnMinutes, coverLimit, startOffset?, endOffset?, exceptions}`. Shift is breakfast/lunch/dinner; weekdays use Sunday=0. Seasons are inclusive local dates. Exceptions are `{date, closed:true}` or `{date, closed:false, startTime, endTime, turnMinutes?, coverLimit?, startOffset?, endOffset?}` and replace the weekly day. End at or before start is next-day. DST gaps refuse; repeated times need the actual selected offset.

`schedule.preview` accepts `{fromDate, toDate, reason, scheduleIds?, renewServiceIds?}` for an inclusive batch of up to 31 dates. Success returns a pending `schedule.publish` proposal containing candidates, physical seats/service covers, conflicts, changed services requiring renewed approval and an exact snapshot. Preview successive batches for longer seasons. Approve using `proposal.approve {proposalId}` or `schedule.publish {proposalId}`. Any intervening schedule/venue/table/service/booking edit invalidates publication. Overlaps refuse publication. Unchanged occurrences are never duplicated. Changed unbooked services renew/close only when explicitly selected in a fresh preview; booked and historical services remain unchanged, with affected-booking handling owed by SERVICE-003. The staff page exposes the editor, preview, explicit renewal selection and approval.

### FLOOR-006 service observations and handover

`booking.stage {bookingId, stage, reason?}` records a staff-observed service or floor step. Owner/admin staff and owner-granted FLOOR-009 hosts record service observations. Operational stages are confirmed, reconfirmed, arrived, partially-arrived, seated, ordering, check-open, paid, clearing, completed, late, cancelled and no-show; course/floor stages are reserved, seated, mains, dessert, check-dropped, needs-bussing and ready. `GET /api/state` adds `serviceStages` with current labels, elapsed whole-minute timers, actor/source and permitted next steps, and retains append-only `state.serviceEvents`. The floor and shift handover expose these same observations. Timers advance without replacing open forms. Legacy missing observations say not recorded.

Paid is an explicitly staff-recorded observation, never a claimed processor payment. Paid/completed leave a dirty table unavailable to new staff seating until staff ready. Future public reservations continue to fit the promised turn/reset; ready never shortens it. `booking.status` remains the existing guarded booking-status door and writes the same observation history. A latest-event correction uses `{bookingId, correctsEventId, reason}` without a stage: it appends a restoration of the original prior state, retains the original and refuses physical clashes. Guest erasure clears linked observation free text while preserving anonymous status accountability. POS-007 inherits every observation and dirty-table rule before connected signals ship.

### ROLE-003 server sign-in

The owner grants/revokes `{operatorId, enabled}` through `team.server`; the target must be an active native member without a host or shift-lead grant, and revoking removes every shift link. A manager links that person to one shift server with `server.save {…, operatorId}` (empty clears; one link per person per shift). A signed-in server reaches only `GET /preshift`, `/api/preshift`, `/api/preshift.pdf`, `/kitchen`, `/api/kitchen` and `/api/floor-version`; `/app` redirects to `/preshift`, and every other door answers 403. The sheet and kitchen view list only shifts the server is linked to, their own sections' tables and parties (guest name, level, occasion, unverified dietary/allergy/access requests; kitchen view with no guest identity), with no contact, guest notes, tags, payments, shift notes, other sections, pacing or dish totals. Read-only members keep their existing read doors and never mutate; guest exports, backups, reminders and report CSVs stay manager/owner-only for hosts, servers and members.

### ROLE-001 venue groups

Each venue is its own installation. The owner of the home venue sends `POST /api/group/invite {label}` and receives a one-use `gi_…` code once (24 hours; only its hash is stored). The owner of the joining venue sends `POST /api/group/join {homeOrigin, code, ceiling}`; `ceiling` lists the most any group admin may read there (`reports.read`, `preshift.read`). The joining venue calls the home venue's `POST /api/group/join-accept`, which claims the code exactly once and returns a link secret that only the joining venue keeps. `POST /api/group/leave` and `POST /api/group/link/revoke {linkId}` end a connection and drop every grant that reached it.

`POST /api/group/admin {operatorId, venues: {home|<linkId>: [rights]}}` replaces one native member's explicit per-venue rights (never above a venue's ceiling); `POST /api/group/admin/revoke {operatorId}` removes them. `GET /api/group` shows the owner every link and grant, and a group admin only their own rights. A group admin exchanges their signed-in session for a short-lived read token with `POST /api/group/token` (shown once, expires in 12 hours). `GET /api/group/reports/reservations` and `GET /api/group/preshift?date=` with `Authorization: Bearer gt_…` return that venue's reservation report or host pre-shift projection when the token holds the right there. A member venue asks its home venue on every call, so revocation stops access at once; if the home cannot be reached the answer is 403. Group tokens are read-only: they cannot reach any other door, write, export, refund, erase, change people or providers, and the venue's own owner and managers keep every grant, export, erasure and provider change as personal authority. Every owner decision is recorded in the audit history, with before/after rights visible only to the owner.

### FLOOR-009 direct assignments

The owner grants/revokes `{operatorId, enabled}` through `team.host`; the target must be an active native member. Native account roles stay unchanged. A granted host can record `booking.stage` / `booking.status` and directly change assignments, but cannot approve proposals, change venue settings or use owner exports. Current state returns the effective actor role and `hostIds`.

Each direct command requires numeric `version` equal to `GET /api/state.version` and accepts an optional `reason`:

- `booking.move {bookingId, tableIds, version, reason?}` moves one active party.
- `booking.swap {bookingId, otherBookingId, version, reason?}` atomically swaps both parties, validating the final floor.
- `booking.lock {bookingId, locked, version, reason?}` changes the assignment lock. Unlock explicitly before a move or swap.

The server checks live physical occupancy, promised turns/reset, ongoing seated parties, seats, distinct tables in exact manager-approved adjacent combinations and exact required access tags. `table.save.accessTags` and booking HTTP `requiredAccessTags` are arrays of up to 20 exact strings; every chosen table must supply every required tag. FLOOR-002/003 and GUEST-003 carry richer attributes and explicit join definitions before shipping. Every action writes exactly one audit row with actor, timestamp, subject, reason and before/after arrays of `{bookingId, tableIds, locked}`; swaps include both parties. Locked assignments refuse prepared moves at prepare and approve, and new booking allocation never mutates an existing assignment. Only preparation keys prepare `table.assign`; people use the direct commands and managers decide agent proposals. Guest erasure clears linked reasons and required access tags.

### FLOOR-005 timeline and overrun

`GET /api/timeline` requires an existing native session or preparation key. Parameters are venue-local service-start `date` (YYYY-MM-DD), optional `serviceId`, `search`, `source` (`online`, `walk-in`, `waitlist`), `status` (`booked`, `seated`, `completed`, `cancelled`, `no-show`), `area`, `serverId`, `zoom` (minutes per time division), and `nextMinutes` (inclusive elapsed arrival window from now). The response has rows with original reservation times, expected departure/reset, corrected staff-observed arrival/seating/departure/ready, late/overdue minutes, collision ids and retained service/assignment/turn histories. Header totals carry the exact displayed booking ids for drilldown. Average actual turn uses observed corrected seating-to-completion among displayed parties completed today in the venue timezone; absent actual observations stay unknown. FLOOR-004 supplies real server assignments/filtering before sections ship.

`booking.extend {bookingId, expectedEndAt, reason}` is a direct host/manager staff observation for a seated party. Expected departure is an offset instant later than now and the current forecast; a reason is required. It appends one audit row and changes no confirmed start/end/reset or assignment. The original reset duration follows the extension for occupancy, and collisions remain visible until a host separately moves a party under FLOOR-009. A still-seated party remains occupied after its forecast passes. No automatic move or connected POS verification is claimed.

### WAIT-002 remote and walk-up joining

`GET /api/public/queue/services` lists open published services, their areas and honest paused state, never guests or queue rows. `/queue` is the standalone website/QR join page. Signed-in staff can display the service QR at `/api/queue-qr?serviceId=...`; it is generated locally and encodes only the public join URL.

`POST /api/public/queue/join` accepts `{serviceId, name, email, phone?, partySize, preferredAt?, preferredArea?, requiredAccessTags?, contactConsent}`. Email uses the existing exact normalized-email guest lookup; shared name/phone never merges. An active same-guest/same-service entry refuses with a generic link/host next action. Preferences are not reservations: preferred time is an offset instant within [service start, service end), area is an existing area, and exact required access tags carry into capacity-checked seating and direct assignments. Contact permission is optional, specific to the queue and never marketing consent. SERVICE-004 channel rules govern public join/update; SERVICE-006 governs actual seating.

Joining returns `{entry, token}` once. Save `/queue#TOKEN` privately: anyone holding it can manage that one party. Only a SHA-256 digest of the 32-byte random token is stored. The response entry contains party/status/preferences/queue contact permission, never guestbook contact fields, private history, other parties or its token hash. All following doors are POST with venue Origin:

- `/api/public/queue/status {token}` reads only that entry.
- `/api/public/queue/update {token, partySize?, preferredAt?, preferredArea?, requiredAccessTags?, contactConsent?}` updates its party; use empty strings/arrays to clear preferences. `{token, leave:true}` leaves the queue.
- `/api/public/queue/rotate {token}` returns a replacement token once and invalidates the old link immediately.

Terminal entries remain readable but cannot be changed/rotated. Owner/admin `waitlist.intake-pause {serviceId, paused}` pauses only new public joining. Owner-granted hosts may use `waitlist.add` and `waitlist.party {waitlistId, partySize, ...preferences}` while paused, without plan approval; pause remains manager-only. Staff intake also returns a token once to hand to the guest, never a claimed send. Public intake/follow-up belongs to an active native owner, with guest-supplied actions honestly labeled. No table hold or delivery is claimed. Erasure invalidates the hash and removes linked preference/permission/history values under DATA-002 and its restore fences.

### BOOK-003 constrained reservation search

Public `GET /api/public/search` accepts venue-local arrival `date` (YYYY-MM-DD, default today), `partySize` (1–500), optional exact `area`, and repeated `requiredAccessTags`. It returns public venue/area/access choices, normalized `query`, `results` and an actionable `message`. Each result has `serviceId`, `serviceName`, `startAt`, `endAt`, `cleanupEndAt`, local arrival `date` and `alternative` (true on a later date). Results use the same live booking rules, shared capacity and full-turn/reset fit as checkout, over the inclusive requested date through seven calendar days later. Unknown areas/tags yield no matching slots; invalid dates/party sizes return 400. No guest data or table inventory is returned.

`POST /api/public/book` additionally accepts exact `area` and `requiredAccessTags` (array). Every allocated table must satisfy both; the booking freezes `requiredArea` and tags so direct/prepared moves cannot lose the promise. Confirmation returns the chosen area and tags. Guest erasure clears these guest-linked requirements under DATA-002. Search is never a hold: commit rechecks current inventory; a losing request returns 400/409, refreshes the same search and requires explicit reselection while retaining contact input. No silent substitution or false booking occurs. EXP-001 and ROLE-001 inherit experience filters and approved sister-venue alternatives before those capabilities ship.

### FLOOR-003 approved physical combinations

Owner/admin people send `combination.save {id?, tableIds, capacity, accessTags, setupMinutes, enabled, adjacent:true}` to `/api/commands`. The full exact set has two or more distinct existing tables; the manager explicitly confirms adjacency. Capacity is at most the sum of their seats, approved access tags must exist on every constituent, and an exact set has one definition. Explicit adjacency can span named areas; BOOK-003 required-area searches still require every constituent match. New allocations use only a single table or one enabled exact approved set, never transitive joins or arbitrary sums. Public search returns times, never the private join snapshot.

Setup is an integer 0–120 elapsed minutes immediately before arrival and must fit within the service. A booking freezes `setupStartAt` and `combination` (id, tableIds, capacity, accessTags, setupMinutes and areas). Half-open setup/turn/reset occupancy participates in all shared-table conflicts, including overlaps between services and overruns. Disabling a join affects new assignments; existing booked/seated snapshots remain usable. Structural edits refuse until active commitments finish. Old joined commitments without a snapshot require a manager to approve their physical join and reassign explicitly before further service actions; their original occupancy remains protected.

Direct move/swap validates current enabled joins, preserves original promised arrival/end/reset, records new setup/snapshot in before/after history and refuses a clash. Lock and later service observations validate existing frozen commitments. Prepared publication/reassignment includes join configuration and refuses after it changes. New tables cannot alter a referenced join’s physical settings silently. All current booking doors enforce this; BOOK-002/005, DIST-001–004, VOICE-001 and AGENT-001 inherit before shipping.

### FLOOR-002 rooms and reviewed floor lifecycle

Managers use `room.save` with `{name, kind}` (`indoor`, `outdoor`, `bar`) and optional `id`. `table.save` accepts `shape` (`round`, `square`, `rectangle`, `bar`), `area` (room name), exact `accessTags`, seats and 0–100 percentage coordinates. Existing named areas remain valid.

Prepare `proposal.prepare` with `kind: "floor.change"`, `reason`, and `plan: {tableId, changes, retire, replacements: [{bookingId, tableIds}]}`. The response contains the exact snapshot, affected commitments, conflicts and `approvable`. Preparing never edits the floor; unsafe previews remain visible but cannot be approved. `proposal.approve` binds the exact snapshot and applies every fitting replacement atomically, retaining confirmed times, room, access needs and assignment history. Changed inputs require a new preview. Locked parties must first be unlocked. Retirement needs an explicit replacement for every active commitment and refuses arrived, seated or unbussed parties; retired records stay in history and cannot take new assignments.

`GET /api/floor-version` is authorized like `/api/state` and returns `{version}` without guest data. Open staff screens check it every three seconds. Focused or unsaved forms defer live replacement with a pending-change label; transport/auth failures show that updates are unavailable.

### FLOOR-004 shift sections, servers and kitchen capacity

Managers configure a service with `server.save {serviceId, id?, name, coverCap}`, `section.save {serviceId, id?, name, serverId, tableIds}`, `server.break {serviceId, serverId, onBreak, reason}`, and `kitchen.save {serviceId, area, coverCap}`. Servers are shift roster labels, with no new account privileges. Sections have exclusive active tables; joins must stay within one section. Active mapping edits are refused until their parties are moved or finished. Existing seated parties may retain their server during a same-section move on break; new assignments and seating cannot use that server.

`GET /api/sections` with `serviceId` and `partySize` query parameters returns current per-server seated/expected covers with booking ids, section tables, kitchen area caps and the eligible rotation. Optional offset `startAt` selects the suggested arrival. Rotation checks full table fit and server/kitchen capacity, then sorts seated covers, oldest last seating and stable id. Caps measure peak concurrent booked/seated dining covers in half-open arrival-to-forecast-departure intervals; ongoing seated parties stay occupied. Expected totals include the shift's booked and seated parties. Setup/cleanup remain separate physical occupancy.

Every existing booking, seating and assignment path rechecks staffing capacity. Bookings carry section/server snapshots and append attributed `servingHistory` events on booking, seating and reassignment. `GET /api/timeline?serverId=…` filters these assignments and returns readable roster names. Owner backups preserve staffing and serving history.

### SERVICE-005 / SERVICE-007 pacing and reviewed exceptions

`service.save.pacing` and owner/admin `service.pacing {serviceId, pacing}` accept `{intervalMinutes, arrivalCovers, arrivalParties, concurrentCovers, areaArrivalCaps:{area:covers}}`. Counts are per service: elapsed half-open intervals aligned to service start, counted booked/seated/completed arrivals and service covers (not cancelled/no-show), and overlapping booked/seated dining covers (ongoing seated remains counted past forecast). A join counts once and against every constituent area. Default new policy is 30 minutes and 500 for each numeric limit with no area caps; older absent policies add no arrival or simultaneous limit beyond existing service covers and FLOOR-004 kitchen caps. Existing commitments remain; later allocations enforce live caps.

`GET /api/pacing?serviceId=ID` returns the interval limits, counts, full markers and exact booking drilldowns, plus separately counted overridden reservations. The reservation report and CSV carry the corresponding filtered pacing override count. WAIT-002 queue intake remains available at caps: queued only; no table or time promised. Seating, booking and allocation enforce pacing.

The owner uses `team.pacing {operatorId, enabled}` for an active FLOOR-009 host. Removing host access removes the pacing grant. Owner/admin and granted hosts preview `POST /api/pacing/preview {command, payload}` for `booking.walkin` or `waitlist.seat`, using the same payload as the command. The no-write result contains every exceeded limit/current/projected/excess and a five-minute `review` HMAC bound to the native actor, command, payload, floor version and expiry. To proceed, send the unchanged command payload plus `pacingReview`, `pacingConfirm:"yes"` and `pacingReason`. A changed floor, payload, expired review or revoked grant requires fresh review. Public/preparation/agent channels cannot override. No review bypasses physical capacity, fit, access, joins, server caps/breaks or occupied turns. Configured FLOOR-004 concurrent kitchen-area caps join the signed area-pacing warnings; server caps remain hard. Unrelated roster edits preserve reviewed kitchen exceptions, while changing a kitchen cap itself still validates existing commitments. Blocked staff starts also require the reviewed pacing exception.

The booking keeps `pacingOverride` and the audit has `booking.pacing-override` with actor, time, reason and limit facts; timeline and reports flag it. Linked reasons follow DATA-002 erasure, including proposal snapshots. Tokens never persist. BOOK-002/005, DIST-001–DIST-004, VOICE-001 and AGENT-001 inherit these guards before new doors ship.

## Service performance (REPORT-002)

An owner or manager reads `GET /api/reports/performance` with query `serviceId=ID`. The response contains `report`, the current floor version and publications for that service. Turn and wait distributions carry finite sample counts, missing counts, exact observation ids, mean, median and nearest-rank p90 in elapsed minutes. The service date is the venue-local service-start date. Histories retain staff observation and correction ids, actors, timestamps and before/after facts; no guest names, contacts, notes or reasons enter the report. Staff quotes are labeled staff-recorded, not delivered provider estimates.

`POST /api/reports/performance {serviceId}` publishes the exact generated facts as an immutable snapshot, with native actor, time and floor version. `GET /api/reports/performance` with query `snapshot=ID` reads it unchanged after corrections and returns `changedSincePublication` when the floor version has changed. Publish again to retain adjusted facts beside the original. These doors have the same manager-only rights as reservation reports; writes require the venue origin. Owner archives include published reports.

Expected turns retain the confirmed arrival/departure; actual turns require corrected seating and completion timestamps. Departure delay compares completion (or now for an ongoing seated party) to the confirmed departure. Quoted wait deviation is actual wait minus the nearest range bound, zero inside the range. Queue abandonment and all disposition totals open their exact queue ids. Missing timestamps and historical serving assignments remain explicit. Historical attended covers use the serving assignment at corrected seating, while current assigned expected covers are separate. Utilization unions observed physical table-seat minutes within service bounds and divides by available table-seat minutes, with ongoing observations identified; it excludes setup/cleanup and does not estimate guest distribution within joined tables. Interval pacing and override drilldowns use the shared pacing ledger.

### BOUND-001 product boundary

Not in Placemat: online ordering, gift cards or the POS itself. Placemat sells no gift cards, stored-value cards or vouchers and takes no online food orders. Gift cards, online ordering and check taking stay in the restaurant’s POS or its payment provider’s own products; connected loyalty stays there too. This release has no payment collection or booking balances. A staff-recorded “ordering” or “paid” stage is only a service observation, never an order or processor payment. No route or command issues, transfers, tops up or redeems stored value. Booking inputs create reservations only; extra financial fields do not create a payment, order or balance.

## No-show review assistance (AGENT-005)

Owner/admin managers read `GET /api/reports/no-show?serviceId=ID` for fact-cited review flags, raw elapsed lead minutes, attendance/reconfirmation reference ids, missing-data caveats and later attendance monitoring. This deterministic assistance assesses no profile notes or protected traits and produces no probability. ### Consent-aware analytics (ct ruling, 20 October 2026)

`analytics.settings {ga4: {enabled, measurementId, debugMode, apiSecret?}, meta: {enabled, datasetId, testEventCode, accessToken?}}` is owner-only (admin, member, host and preparation keys get 403). `measurementId` is `G-` plus 4–16 letters or digits (stored uppercase); `datasetId` is the Meta Pixel/dataset ID, 6–20 digits; `testEventCode` is blank or 4–20 letters/digits (stored uppercase). Switching a provider on needs its ID and a key, either saved or entered now. Keys are 8–200 (GA4 API secret) or 20–1000 (Meta access token) characters without whitespace; a blank key keeps the saved one, an entered key replaces it, and switching a provider off stops its events while its key stays saved. An unchanged save is 409. Keys are kept only in `pm_analytics_keys`, written in the same version-fenced D1 batch as the settings, and no response returns them: `state.analytics` holds the settings, and the owner's `GET /api/state` adds `analytics: {keys: ['ga4'|'meta'...], results}` naming which keys are saved and each provider's answer to its most recently sent event `{provider, event, status, detail, at}` (`at` is when that event was handed over for sending, so a slower answer to an earlier event never replaces it). The audit row `analytics.settings` keeps actor, time and `before`/`after` settings with `keySaved` (and `keyEntered` when a key was typed in that change), never a key.

`analytics.remove-key {provider: 'ga4'|'meta'}` is owner-only too (ct ruling, 21 October 2026; admin, member, host and preparation keys get 403; an unknown provider is 400). It deletes that provider's saved key from `pm_analytics_keys` in the same version-fenced batch and returns `{provider, keys}`; with no saved key it is 409. The provider's settings are unchanged, so one that is on without a key is left out of `GET /api/public/services` `analytics` and sends nothing, the settings say a key is needed, and a settings save that keeps it on needs a newly entered key. The audit row `analytics.remove-key` (subject the provider) keeps actor, time and `before`/`after` settings with `keySaved` false and `keyRemoved: true` for that provider, never a key. Restores never bring a key back.

`GET /api/public/services` adds `analytics`: the providers that are on and hold a key (`[]`, `['ga4']`, `['meta']` or `['ga4','meta']`). When it is not empty, `/book` and the widget ask once per page visit (Accept / Decline), naming each listed provider and what is sent; the answer and the random visit ID (`crypto.randomUUID()`, created on Accept) exist only in that page's memory. Without Accept the page sends no analytics request and no visit ID.

`POST /api/public/analytics {event: 'search'|'checkout-start', visitId, partySize, embedOrigin?}` (same-origin, at most 60 a minute per network, 202 `{providers}`): `visitId` must be a version 4 UUID, `partySize` 1–500, and `embedOrigin`, when sent, a listed widget origin (400 otherwise). The page sends `search` after each search the guest runs and `checkout-start` each time the guest selects a time. `POST /api/public/book` accepts `analytics: {visitId}`; after the booking commits, the server sends the completed-booking event. A missing or malformed visit ID sends nothing and never affects the booking. The visit ID is not stored on the booking or anywhere else.

Every send runs after the guest's response (`waitUntil`), once, with a 10-second timeout and no retry queue, so a slow or failing provider never blocks or delays a booking. Requests, field for field (source = `widget` with the listed origin, or `booking-page`):

- GA4 Measurement Protocol: `POST https://www.google-analytics.com/mp/collect?measurement_id=<id>&api_secret=<secret>` with `{client_id: <visit ID>, events: [{name: 'search'|'begin_checkout'|'placemat_booking', params: {party_size, booking_source: 'widget'|'booking-page', widget_origin?}}]}`; test mode adds `debug_mode: true` and `engagement_time_msec: 1` to `params` so events appear in DebugView.

No request carries guest name, email, phone, IP address, cookies, booking reference or reservation date/time, and no provider script loads on any Placemat page (CSP `script-src 'self'`, `connect-src 'self'`). Results are honest labels: GA4 answers without confirming events (`Sent. GA4 does not confirm events; check DebugView.`), Meta reports `events_received`; a refusal or unreachable provider is recorded as such, and a demo installation records that nothing was sent. This narrow foundation does not claim PAY-005 signed-event, guest notice, fee/report or live sandbox acceptance. ROLE-001/ROLE-004 retain future venue/group/provider boundaries. ### Booking-bound deposit requests

Full managers create `payment.request {bookingId,amountCents,dueAt,followupOwnerId,reason}`. The USD amount and deadline are immutable in this foundation. Hosts or managers explicitly issue `payment.link {requestId}` against the saved request and copy/share the returned Stripe-hosted URL; issuing it never records message delivery. A PIN host has the same link authority, without amount/settings/waiver/refund authority. `payment.sync {requestId}` retrieves matching server-side Stripe data; only verified paid state establishes payment. The floor, timeline, reservation follow-up and pre-shift sheet show unpaid deadlines; callback completion never marks money paid. Requests and refund records have documented CSV/archive coverage, with hosted guest URLs redacted and provider references retained. Worker `STRIPE_SECRET_KEY` stays outside business data. PAY-005/PAY-010 remain partial for their original provider delivery, policy automation, reconciliation and sandbox acceptance.


### Private reservation management

`booking.management.send` on `POST /api/commands` requires a full owner session and `{bookingId, acknowledged:true}`. It emails the recorded reservation contact through the configured production sender and returns provider acceptance metadata, never the bearer. Reissue revokes the previous link. A failed or uncertain submission revokes the issued capability; no automatic retry occurs. Demo and local-auth modes refuse outbound sends.

`GET /manage-booking` opens the existing guest booking shell. Its email link carries a fragment capability, removed from page history at startup. Same-origin JSON posts to `/api/public/booking-management/status`, `/preview` and `/commit` carry `token` in the body. Status returns only that reservation and contact. Preview accepts `action: change|reconfirm|cancel`; changes may include an offset `startAt`, integer `partySize`, and reservation-only `contact: {name,email,phone}`. Its response includes the exact preview id and fee/refund consequences. Commit accepts only `{token,previewId,acknowledged:true}` and rotates the token atomically with the confirmed mutation. Failed availability preserves the original booking.

Tokens expire within 24 hours and no later than service start. Rotation preserves expiry. Altered, foreign, expired, replayed or externally changed reservation links return a generic 404; concurrent inventory/authority changes refuse with 409. Public requests are origin-checked and rate-limited. Token records are excluded from archives and erased with the guest; reservation contact data follows business CSV/archive validation and erasure. Current financially implicated reservations require manager review; no fee/refund action is invented or automatically submitted. These custody defaults await ct approval, and BOOK-004 remains PARTIAL.

### Refund outcome reconciliation

`POST /api/payments/refund-events` is a provider door, without a cookie or browser Origin. The unread request bytes require a current `Stripe-Signature` authenticated by the installation's `STRIPE_WEBHOOK_SECRET`. New matched events retrieve the current refund with `STRIPE_SECRET_KEY`; mismatched money/booking/processor references refuse. Accepted event IDs deduplicate atomically, and stale notifications never overwrite current Stripe state. Failures assign the original submitter an owned follow-up. Missing configuration fails closed. No webhook creates a processor refund or sends mail.

A personal owner explicitly calls `payment.refund-notice` with `refundId`, the reviewed `outcome` and `acknowledged: true`. It sends one transactional email for that refund/outcome to the reservation's recorded contact. A changed outcome, manager/host/agent identity, destination/channel override or missing acknowledgment refuses. The immutable notice names the refund amount, actual saved outcome and remaining refundable balance after pending/succeeded refunds. Duplicate requests return the saved attempt, including an uncertain attempt; they never resend. The page reports provider acceptance and leaves actual mailbox delivery unconfirmed. SMS and automatic retries are not implemented. PAY-005 remains partial for the named financial/report and custody gaps in CONTRACT.
