# Portable business records

The owner can download current business records at `GET /api/business-export/<kind>.csv`, using a native owner session. The fixed kinds below include all stored statuses, including drafts, cancelled bookings, resolved queue entries and declined proposals. Optional collections produce a header-only file when absent. There is no subscription, billing check or provider connection required to export or restore supported records. Downloaded files contain private guest information and need private storage.

CSV exports are for inspection and transfer to another system. They are not accepted by the venue backup restore or the guest move-in importer. Use the [structured backup](backup-and-restore.md) to move a supported installation and its import/erasure custody records. CSV downloads read current records without sending messages, approving plans, changing reminder status or recording provider delivery. Separate CSV requests can observe different revisions if staff are editing; use one structured backup when a consistent installation snapshot is required.

## CSV format, links and version

Files use UTF-8, comma delimiters, a header row, CRLF record separators and a final CRLF. Every cell is double quoted; quotes inside cells are doubled and embedded newlines are preserved (RFC 4180). A cell whose first non-whitespace character is `=`, `+`, `-` or `@` receives a leading apostrophe, including when spaces, tabs, newlines or a byte-order mark precede the character. This protects spreadsheet opening; programmatic readers should use `data_json` for original scalar values rather than stripping apostrophes indiscriminately. A phone beginning `+` and a negative number can therefore have this protective prefix in their scalar column.

Every kind has two common columns:

| Column | Meaning |
| --- | --- |
| `csv_version` | Business CSV schema version, currently `1`, independent of the archive version. |
| `data_json` | The complete current record as JSON, after the exclusions and erased-guest treatment below. Contains optional and nested fields, not just the scalar projections. JSON strings retain original content; property order is not a contract. |

Columns ending `_json` contain JSON for the corresponding property without that suffix. A missing optional property produces an empty CSV cell; explicit JSON null is `null` in a JSON column. Scalar null and absent properties both produce empty cells; `data_json` distinguishes them. Booleans use `true`/`false`, numbers use their stored numeric value, and JSON arrays retain order. Missing collections are not invented. The exporter does not infer defaults, historical dates, consent, delivery or outcomes.

Column names below match the stored camelCase fields. New optional fields can appear in `data_json`; a breaking change to a column's name or meaning requires a new `csv_version`. Consumers should read headers and ignore unknown columns. An empty kind has no row version; this document and the exported `businessCsvVersion` identify its schema. Unknown kind names return 404; filenames cannot select arbitrary tables or fields.

`id` is the stored stable identifier of that row; keep it as text. `guestId` joins to `guests.id`, `serviceId` to `services.id`, `bookingId` to `bookings.id`, and `tableIds` entries to `tables.id`. `scheduleId` joins to `schedules.id`. `serverId` and `sectionId` join to the servers and sections inside the linked service's `staffing_json`. `combination.id` links to `combinations.id` when the current definition still exists; the booking retains its own exact snapshot. Rooms are connected to tables by `tables.area = rooms.name`, not a room identifier. Retired/deleted definitions and snapshot references may not have a current matching row.

Actor/owner/preparer/approver identifiers and provenance references remain as recorded; they are not credentials. Native sign-in identities and agent key records are excluded, so their IDs may have no exported directory row. `audit.subject` identifies the object appropriate to its action (for example a booking, service, queue entry or proposal). Nested proposal plans may refer to several kinds. Unchanged IDs and nested reference fields allow reconciliation without copying access credentials.

Unless stated otherwise, `*At` values are recorded timestamp strings, normally explicit-offset instants; missing timestamps mean not recorded. Schedule local dates/times and imported guest-history dates retain their original representation. `venue.timezone` supplies the IANA zone for local interpretation. Counts and durations are people and minutes respectively. Financial amounts are integer USD cents, with `100` meaning $1.00; each charge/request retains `currency: usd`.

## Exclusions, erasure and current limits

Business CSVs include the current venue state, guest records and retained published performance-report snapshots. They exclude native auth accounts/sessions/sign-in links, agent keys, environment/configuration values, provider credentials, transient request/review tokens, rate limits, import staging/journals/original artifacts and erasure identity hashes. Historical import custody is included by the structured archive where retained. No independent attachments are currently modeled by this exporter.

Every JSON object is scrubbed recursively, including proposal snapshots and history details. Property names are normalized to lowercase ASCII alphanumerics; properties whose normalized names contain `token`, `secret`, `password`, `credential`, `bearer`, `authorization`, `cookie`, `apikey`, `privatekey` or `session` are omitted. Normalized `providerurl`, `providerreturnurl` and `processinguntil` are also omitted. In particular, waitlist `managementTokenHash`, inquiry `tokenHash`, hosted Checkout URLs and local refund processing leases are absent from scalar columns, nested JSON and `data_json`. The dedicated payment-request CSV projects its non-secret Checkout Session identifier as `providerReference` so that reference remains portable. Their omission does not remove guest IDs or source/reference IDs. The scrubber does not guess whether arbitrary user-written prose contains a secret; retained business text remains business data.

DATA-002 erasure sanitizes guest-linked booking requests, queue preferences/contact permission, inquiry messages/offers, task reasons/outcomes, audit/service reasons and retained proposal copies before export. Audit snapshots linked to the erased guest are replaced with redaction markers, retaining the change kind, record ID, actor, action and time. The CSV generator also independently replaces any `erased: true` guest object with the canonical tombstone: its `id`, name `Erased guest`, empty email/phone/notes, empty history and `erased: true`. Old profile/provenance/note-history or unexpected extra values on such a guest cannot escape through its direct row or JSON. Anonymous operational times, status, counts and accountability references remain. CSVs cannot retrieve personal values already erased, but erasure cannot revoke a copy someone downloaded earlier.

The financial foundation retains staff deposit requests, their Stripe session references, synchronized captured charges, refund reservations/outcomes and refund audit events. It does not establish complete PAY-010 collection/delivery/waiver or PAY-005 notice/webhook journeys. Card details, ticketed experience/add-on inventory, marketing subscription/preferences ledgers, delivered SMS/email outcomes, voice conversations and stored media attachments remain outside the currently stored records. Queue contact permission is the explicit consent currently stored; it is not marketing consent. Inquiry conversations and approved reminder drafts/export records are the message records currently available. Nonportable card secrets (PAN, CVC, magnetic-stripe/track data, provider card tokens) and provider/API secrets are not collected into this export. New supported domains need their own documented records/exclusions before claiming full DATA-003 coverage.

## Structured archive version and custody

The owner HTTP backup is a JSON array containing the same manifest/part/closing records used by the CLI archive. CLI `.rer` packaging is handled by the portability module. The structured manifest uses `format: runeditrun-portability`, `version: 2`, and `product: hospitality/placemat`; this is separate from business CSV version 1. Version 1 archives lack authenticated restoration/erasure binding and are refused by the normal reader.

The manifest records export time, source installation identity, schema identity, table schemas/counts/dependencies, excluded table/column inventory, required configuration names, part count, erasure epoch/journal and, where supplied by the runner, applied migrations. Parts carry ordered rows and checksums; the closing record carries content and archive hashes. These integrity hashes are not guest-management credentials. Restore validates integrity, relationships, compatible schema and erasure fences before applying supported data into an empty destination. It refuses an older known pre-erasure archive; supply a trusted later same-source erasure journal when moving older data to a new installation. See [backup and restore](backup-and-restore.md) for the supported actions.

The archive excludes native `oa_*`/`oc_*` auth records, platform-owned transient/bookkeeping tables, `pm_agent_keys`, `pm_public_limits`, `pm_assertions`, `pm_analytics_keys` (the BOOK-002 GA4 API secret and Meta access token, write-only secrets) and `pm_analytics_results` (each provider's latest answer). The exact inventory is present in each manifest's `excludedTables`. Durable import custody and erasure fences travel; archived import originals are subject to erasure withdrawal. Re-enter configuration through setup: `OWNER_EMAIL`, `SESSION_SECRET`, `SETUP_TOKEN`, `AUTH_ORIGIN`, `MAIL_PROVIDER` and `MAIL_FROM` are required configuration names, not exported configuration values. Staff sign-ins and agent keys must be established in the destination. A restore brings back BOOK-002 analytics settings without keys, so the restored venue asks no analytics question and sends nothing until the owner enters the GA4 API secret and Meta access token again.

Financial tables `pm_payment_requests`, `pm_refund_charges`, `pm_refunds` and `pm_refund_events` travel as supported structured records. Every exported `pm_payment_requests.provider_url` is replaced with null: a hosted Stripe Checkout URL is a private payment-access link. This canonical row redaction preserves the table's columns and the existing manifest exclusion inventory. The archive retains the Checkout Session ID, exact attempt timestamp and original return URL so an unresolved request can be reconciled without changing its idempotency parameters. Refund `processing_until` leases reset to zero in the exported records. Worker configuration, including the Stripe secret key and host-PIN peppers, is never archived; configure the original merchant account separately before reconciliation. Restore itself never contacts Stripe, charges, refunds, sends a link or claims delivery. For a restored recorded session, explicitly synchronize it to retrieve its current provider-verified link/status; do not create a replacement session. An unresolved creation attempt outside the provider idempotency guarantee needs owner reconciliation before another attempt.

Restore validates payment/refund integer amounts and USD currency, unique request/provider references, booking relationships, refund-to-charge booking matches, reserved balances, event snapshots and the event chain against each current refund. Recorded actor IDs remain historical references; restore does not recreate their sign-ins or authority. Erasure removes linked financial free-text reasons and hosted URLs while retaining amounts, status, timestamps and references; later archives and CSVs export those sanitized facts, and the existing erasure custody fence applies to restoring earlier copies.

Unlike business CSVs, the current structured archive preserves live waitlist `managementTokenHash` and inquiry `tokenHash` inside venue state so existing private links can be restored. It does not contain the original raw bearer tokens. These digests are sensitive restoration data; keep archives private. Guest erasure removes the affected digests before later backups and restore fences protect against bringing erased data back. The CSV generator intentionally applies its stricter credential scrub without changing this restoration policy.

FLOOR-013 adds `services.preorderItems_json` (immutable item id/name, active publication flag), `services.managerPreorders_json` (itemId, integer quantity, actor, at) and `bookings.preorders_json` (itemId, preserved itemName, integer quantity). Item IDs join to the linked service’s list. Quantities are unpaid dish requests, never payment, fulfillment or safety confirmations; guest-supplied booking totals and manager counts remain separate. Note text/history on an erased guest’s booked service dates is cleared with its audit snapshots, because shared instructions can repeat guest facts; booking preorders and needs are removed, while anonymous manager counts and accountability remain. Structured restore validates note dates/history and item/count/booking relationships before any product writes.

SETUP-001: venue `setup_json` and the structured venue record include legal/trading details, address, US phone, contact channels, the uploaded restaurant logo, USD, editable new-service channel rules, and the owner acknowledgment (actor, instant, version, exact rules). Restore validates these fields before publication. Guest responses expose only trading name, timezone and intentional restaurant contact/branding fields.

GUEST-004 adds `guest-merges.csv`: id, guestId, duplicateId, status, createdAt/createdBy, unmergedAt/unmergedBy, purgedAt, snapshots_json and pendingAssignment_json. Each snapshot includes original/merged guest values and versions, linked booking/queue/reminder/inquiry before/after records and the pre-merge audit ID baseline. Guest CSV adds mergedInto and contacts_json (kind, value, sourceGuestId, provenance); absorbed aliases remain in complete exports though ordinary guest lists hide them. Queue contactPhone binds permission to the original contact; approved reminders carry contactName/contactEmail/contactPhone.
